# Lemuria Park — архитектура экосистемы

**Статус: зафиксировано 18 августа 2026.**  
Это не один сайт. Это четыре продукта на одной backend-архитектуре и одной PostgreSQL.

Код: один Next.js 15 (этот репозиторий).  
Данные: одна база. Не дробить кассу / директора / owner по разным БД.  
Инфраструктура: только российские сервисы (Yandex Cloud + ЮKassa).

`docs/ARCHITECTURE.md` описывает текущую реализацию в коде. Этот файл — целевая модель, от которой не отклоняемся без явного решения.

---

## 1. Четыре интерфейса

| Продукт | Хост | Кто | Смысл |
|---|---|---|---|
| Public | `lemuriapark.ru` | гости | Сайт, сеансы, покупка билетов |
| Cashier | `cashier.lemuriapark.ru` | кассир | Смена, продажа, QR, заказы |
| Director | `admin.lemuriapark.ru` | директор / администратор локации | Операции доступных локаций |
| Owner | `owner.lemuriapark.ru` | собственник | Глобально: деньги, города, риски, система |

Физически: один Next.js с host/routing rules. Дешевле, безопаснее, без дублирования доменной логики.

Staging: `stage.lemuriapark.ru` (публичный контур staging). Внутренние staging-хосты: `cashier.stage.lemuriapark.ru`, `admin.stage.lemuriapark.ru`, `owner.stage.lemuriapark.ru` — либо path-режим на одном staging-хосте до включения DNS.

### Соответствие текущему коду

| Хост | Сейчас в репозитории | Дальше |
|---|---|---|
| Public | `(public)` / `/` | заморозить визуал после чеклиста §8 |
| Cashier | `/cashier` | отдельный продукт, mobile/tablet first |
| Director | `/director` | хост `admin.*`, не путать с ролью `ADMIN` |
| Owner | частично `/admin` | **не** копия директора с большим ACL; отдельный executive-уровень |

Роль `ADMIN` ≠ хост `admin.lemuriapark.ru`. Хост `admin` — продукт директора. Роль `ADMIN` — служебная (создание пользователей, техника) и живёт ближе к owner-контуру.

Внутренние порталы: `noindex`, отдельные cookies-контуры по хосту, CSP, без публичной регистрации.

## 2. Одна логика билетов

Онлайн и касса используют:

- один `Session`
- одну `capacity`
- одну транзакционную проверку мест

Отдельного пула мест «для офлайна» нет. Цену считает только сервер. QR выдаётся только после `PAID`.

| Канал | Как становится PAID |
|---|---|
| Онлайн | только подтверждённый webhook ЮKassa |
| Касса наличные / терминал | сразу PAID (продажа кассира) |
| Refund | отдельный поток, idempotency обязательно |

Интеграции не врут: нет ЮKassa → заказ не «оплачен»; нет Postbox → UI не говорит «письмо отправлено».

---

## 3. Роли и доступ

Публичной регистрации кассиров и директоров нет. Пользователя создаёт `OWNER` / `ADMIN`.

Порядок входа: временный пароль → обязательная смена.

| Роль | Контур | Область |
|---|---|---|
| `CASHIER` | cashier | назначенные локации; смена обязательна для продаж |
| `DIRECTOR` | admin (директор) | только доступные локации |
| `ADMIN` | owner / служебное | пользователи, техника, не «ещё один директор» |
| `OWNER` | owner | все города, интеграции, system health |

Можно назначить одну или несколько локаций.  
Сессии: httpOnly cookies, server-side RBAC, revoke, audit всех критичных действий.

В кассе нет аналитики директора.  
Owner не зависит от одной конкретной локации.

## 4. Визуальный контракт трёх внутренних продуктов

Родственники по токенам (`docs/internal-design-system.md`), но не одинаковые экраны.

| Продукт | Характер |
|---|---|
| Cashier | Максимально быстрый. Большие кнопки, минимум текста. Mobile/tablet first. Нижняя навигация + QR на телефоне |
| Director | Рабочий dashboard: графики, таблицы, расписание, контент, смены |
| Owner | Executive dashboard: деньги, сравнение городов, риски, system health. Не director++ |

Публичный сайт (awwwards) визуально отделён и после заморозки не пересобирается «под кассу».

### Касса (состав продукта)

вход → открытие смены → сеансы → продажа → наличные/карта → QR → заказы → профиль → закрытие смены

### Директор (состав продукта)

сегодня, аналитика, заказы, билеты, расписание, цены, типы билетов, локации, сотрудники, смены, контент, audit  
только свои локации

### Owner (состав продукта)

глобальная аналитика по городам, пользователи, роли, интеграции, платежи, system health, audit, все локации, технические настройки

## 5. Данные: одна PostgreSQL

Не Supabase. Не зарубежный DBaaS.

Модели (логические, не дробить по продуктам):

Users, Locations, Sessions, TicketTypes, Prices, Reservations, Orders, Payments, Tickets, CheckIns, CashierShifts, CashOperations, Refunds, AuditLog, CMS, Media, OperationalEvents.

Медиа: файлы в Object Storage, в Postgres только ключ / URL / metadata.

---

## 6. Инфраструктура — только Yandex Cloud

Каталоги: `lemuria-production` и `lemuria-staging` (отдельные БД, bucket, secrets).

| Задача | Сервис |
|---|---|
| PostgreSQL + backup/PITR, 152-ФЗ | Managed Service for PostgreSQL |
| Фото, hero, галерея, QR-assets | Object Storage (S3-совместимый) |
| Приложение | Serverless Containers (+ VPC к Managed PG) |
| Образы | Container Registry |
| HTTPS | Certificate Manager (Let’s Encrypt) |
| DNS | Cloud DNS |
| Транзакционные письма | Postbox (SMTP/API). Без настройки — не «отправлено» |
| Cron (expire reservations / awaiting-payment / ops) | timer-trigger Serverless Containers |
| Observability | Monium |
| Аудит облачных ресурсов | Audit Trails **плюс** прикладной `AuditLog` |
| Оплата | ЮKassa (отдельный кабинет, не «яндексовый платёж») |
| Секреты | Lockbox / env контейнера. Никакого `.env` в git |

Карты на публичном сайте: Яндекс Карты, не Google.

Деплой: один image tag. Staging PASS → тот же tag в production.

## 7. План (порядок, не параллелить вслепую)

1. **Заморозить публичный сайт** после визуального чеклиста §8. Дальше public не открывать как «ещё одна фича-свалка».
2. **Зарегистрировать Yandex Cloud**: production + staging каталоги, VPC, SA, Managed PG, Object Storage, Registry, Serverless Container, Certificate Manager, Cloud DNS, Postbox, Audit Trails, Monium.
3. **Домены и сертификаты** на четыре хоста + staging.
4. **Production PostgreSQL** — одна БД, миграции из этого репозитория.
5. **Доступ**: OWNER создаёт персонал, временный пароль, RBAC, revoke, audit.
6. **Касса как отдельный продукт** на своём хосте.
7. **Директор** на `admin.*`.
8. **Owner** на `owner.*` как отдельный уровень обзора.
9. Общая логика билетов не разъезжается.
10. ЮKassa + честный webhook; касса PAID сразу.
11. Медиа в Object Storage.
12. Письма через Postbox + SPF/DKIM/DMARC + delivery status.
13. Cron через timer-trigger.
14. Безопасность: отдельные SA, rate limit, CSP, RBAC, backups, restore drill, noindex внутренних порталов.
15. Staging PASS (онлайн, касса, смена, QR на живом iPhone/Android, refund, email, storage, director, owner) → production.

Первым делом после заморозки public: Yandex Cloud (окружения, PG, Storage, DNS, сертификаты, SA). Затем Postbox и ЮKassa. Внутренние системы без этих костылей не «доделываем на localhost как прод».

## 8. Заморозка публичного сайта

Доделывается только текущий визуал, затем public = дизайн-закрыт.

| Пункт | Состояние на фиксации |
|---|---|
| Убрать «Атмосфера зоотеатра» | сделано (галерея не рендерится на главной) |
| FAQ 4–5 вопросов перед покупкой | сделано (лимит 5) |
| Отзывы бегущей строкой | сделано (оценки 4/5, без длинных тире) |
| Карта / «Где мы» | есть; не переоткрывать без бага |
| Footer | есть; не пересобирать |
| Mobile главной | проверить ещё раз перед freeze-signoff |

После signoff: правки public только как баг (билеты, цена, ёмкость, сломанный layout), не как новый маркетинг-блок.

## 9. Правила для разработки

- Не копировать доменные сервисы «для кассы отдельно».
- Не считать `/admin` в коде готовым owner-продуктом.
- Не тащить графики директора в кассу.
- Не писать в UI «отправлено» / «оплачено», если провайдер не подтвердил.
- Не использовать зарубежный hosting, почту, аналитику, хранилище, DNS.
- Staging и production — разные каталоги и secrets.
- Seed (`ChangeMe123!`) в production запрещён.
