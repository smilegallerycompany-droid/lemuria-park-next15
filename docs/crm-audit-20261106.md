## Статус и границы

Аудит НЕ завершён: вход владельца production выполнен через защищённую
форму; консоль Yandex Cloud требует SmartCaptcha. Проверки каждой должности, каждого
состояния кнопок, production-логов и cloud staging ещё не выполнены.
Не было production-заказов, платежей, возвратов, миграций, изменения прав
сотрудников или удаления данных.

Публичный health CRM сообщил SHA `10a09198e3982e8aa82ed8583644ff6b0637f79b`
и `database=ok`. Источник кандидата — ветка
`fix/public-sessions-metrika-20261101`, commit `334b6a3`.
Это НЕ полный воспроизводимый исходник текущей production-системы:
`docs/crm-admin-report-release-20261104.md` и скрипт
`check-live-staff-policy.cjs` описывают compiled-overlay release с
ONLINE_MANAGER, readOnly, отдельной финансовой службой и ограниченным ADMIN;
в доступной Prisma-схеме и политике этих возможностей нет.
Новый SHA health у overlay означает версию сборщика, а не идентичность всех
файлов образа исходникам этого SHA.

Кандидат исправляет доступный исходник. Его нельзя целиком выкатывать поверх
production до восстановления соответствия исходников фактическому образу.

## Проверено непосредственно на production

- HTTPS CRM открывает штатную страницу входа сотрудников.
- Live и ready доступны; ready сообщает `database=ok` (только подключение).
- 28 существующих GET API сотрудников без авторизации вернули 401:
  auth/me; admin system/users/integrations/dashboard/payments; director
  ticket-types/prices/overview/shifts/staff/schedule/audit/locations/analytics/
  me/content/sessions/orders/tickets/content/gallery/content/faq; cashier
  shift/locations/me/profile/sessions/orders. Никакие записи не запрашивались
  с правами другого сотрудника, токены не создавались.
- Контейнерные логи, фактический состав зависимостей образа и доступность
  private staging не проверены из-за отсутствия авторизованной консоли.
- После защищённого входа проверены загруженные обзор, список заказов,
  финансовый отчёт, аналитика выбранной локации, цены, список сотрудников
  и настройки. Оболочки смен, билетов, расписания и сеансов открываются;
  их начальное loading-состояние не считается полноценной проверкой данных.
- В финансовом отчёте явно указано исключение онлайн-заказов. Билеты, корм,
  Балабас и фото показаны отдельно; «Итого выручка» объединяет их.
  Корректность ненулевых сумм не доказана проверкой пустого периода.
- Ссылка «Заполнить отчёт» ведёт на аналитику с `source=CASHIER`.
  Выбор Саратова меняет пояс аналитики на Europe/Saratov и загружает отчёт.
- В кабинете владельца существует форма изменения цен с отдельными буднями,
  выходными и типами билетов; сохранение и выключение не выполнялись.
- Обзор показывает три давно открытые смены и предупреждение, что cleanup
  ещё не фиксировался. Это требует сверки с сотрудниками и журналами, но не
  даёт основания автоматически закрывать смены или очищать записи.
- В общем обзоре саратовские сеансы отображаются на час раньше публичного
  расписания; источник содержит общий форматтер Europe/Moscow. Для смешанных
  списков нужно показывать локальное время и явный пояс, затем проверить
  соответствие одного sessionId во всех интерфейсах на фактическом артефакте.

Предыдущая проверка в 19:59 МСК обнаружила Application error
`3819059684` и ошибки загрузки дат. Свежий healthy endpoint не доказывает
устранение этого инцидента. Для установления причины нужны логи контейнера
за время сбоя; связь с idle-disconnect PostgreSQL пока только гипотеза.

## Зависимости

`npm audit --omit=dev`: исходно 1 critical + 8 high; после обновления
0 critical + 8 high + 1 moderate (9 узлов дерева, не 9 отдельных эксплойтов).
Остались advisory для Prisma/config/deepmerge-ts, nanoid, PostCSS,
sharp, source-map-js и Zod; Next отмечен через вложенный PostCSS.
Данные относятся к локальному lockfile, не к проверенному production-образу.
Массовый `audit fix --force` не применялся: обновление Zod/Next на новую
major-версию требует отдельной совместимости и staging. В конфигурации
изображений `unoptimized=true`; это ограничивает применимость части advisory,
но не заменяет обновление зависимостей.

## Рекомендуемый порядок

1. Сохранить полученную сессию CRM; восстановить доступ к Cloud и прочитать логи инцидента.
2. Получить исходники, соответствующие актуальному immutable production digest,
   сохранить прежний digest и конфигурацию для отката. Не копировать секреты
   или production-данные в публичный GitHub.
3. Перенести исправления на эту базу; сверить ADMIN/ONLINE_MANAGER/readOnly
   с фактической бизнес-политикой, не менять роли сотрудников автоматически.
4. Воспроизводимая сборка и матрица действий/запретов в отдельной staging БД.
5. После PASS опубликовать проверенный immutable image, проверить UI и API,
   записать фактические digest/revision, сохранить возможность отката.

Только после этих шагов можно честно подтвердить проверку всей актуальной
системы и каждой роли. Этот документ не является актом полной приёмки.
